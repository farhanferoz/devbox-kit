# Clipboard bridge: copy, paste and screenshots for Claude Code over SSH

When Claude Code (or `agy`) runs on a headless box you reach over SSH, three things break:

1. **Copy does not reach your machine.** Claude Code picks a clipboard tool only when the
   environment names a display; on a headless box none is named, so it falls back to OSC 52,
   which many terminals (every VTE terminal: GNOME Terminal, Ptyxis) silently drop.
2. **Image paste is impossible.** Claude Code reads a pasted image by running
   `wl-paste --type image/png` or `xclip ... -o`. A headless box has no clipboard to read.
3. **The mouse belongs to Claude Code.** That is fine and needs no fix (below), but it makes
   1 and 2 look like selection problems.

The bridge fixes 1 and 2. On the box, small stand-ins for `wl-paste`, `wl-copy` and `xclip`
(`clip_shim.py`, installed in `~/.local/bin`) send each request through an SSH reverse tunnel
to the machine you sit at, where `clipboard_bridge.py` reads or writes the real clipboard.
Claude Code is not patched: it runs the same commands it always runs, and `Ctrl+V` pastes a
screenshot as it would locally.

```
  machine you sit at                               the box (headless)
  ──────────────────                               ──────────────────
  clipboard_bridge.py  127.0.0.1:18377             claude / agy
    Linux: systemd socket (starts on demand)         └─ runs `wl-paste --type image/png`
    macOS: launchd agent                                    │
          ▲                                                 ▼
          └──── ../tunnels: one always-on ssh -R ◄── ~/.local/bin/wl-paste (clip_shim.py)
```

Requests carry a shared token (`~/.config/clipboard-bridge/token`, mode 600 on both ends,
generated by the installer and never printed). The listener is loopback-only on both ends.

## Install

Prerequisites: the box is set up as in [session/README.md](../session/README.md) (key login,
an ssh alias). On the machine you sit at: `python3`; on Linux `wl-clipboard` (Wayland) or
`xclip` (X11); on macOS optionally `brew install pngpaste` (faster screenshot paste).

```bash
cd ~/dev/devbox-kit/clipboard
./install.sh mybox --selftest      # mybox = your ssh alias (default: $REMOTE_SESSION_HOST)
```

It is idempotent. Steps: detect the clipboard here, create the token, start the bridge
service (Linux: socket-activated systemd user unit; macOS: launchd agent), carry port 18377
to the box with [../tunnels](../tunnels/README.md), copy the token and the stand-ins to the
box, and add `export WAYLAND_DISPLAY=clipboard-bridge` to the box's `~/.bashrc` (fault 1:
that variable is what makes Claude Code choose a clipboard tool; nothing opens a display).
`--selftest` then proves each direction for real and puts your clipboard back afterwards.
Reconnect once (or start a new `box` session) so the session picks up `WAYLAND_DISPLAY`.

Check any time, changing nothing: `./install.sh mybox --verify`. On Linux a daily timer runs
that check and raises a desktop notification if it fails.

## Using it

| You want to | Do |
|---|---|
| paste a screenshot into Claude Code | copy it on your machine, `Ctrl+V` in Claude Code |
| paste text | `Ctrl+Shift+V` (clipboard) or middle-click (mouse selection, Linux) |
| copy from Claude Code to your machine | its copy command, or drag-select inside it |
| select with the terminal instead of Claude Code | hold `Shift` while dragging |

**Do not set `CLAUDE_CODE_DISABLE_MOUSE=1`.** With mouse reporting on, Claude Code scrolls
correctly; with it off, the terminal turns the wheel into arrow keys. The installer removes
the variable from the box's `~/.bashrc` if it finds it.

## Copy without any bridge: OSC 52 (macOS terminals)

If your terminal implements OSC 52 (Ghostty; iTerm2 with *Settings → General → Selection →
Applications in terminal may access clipboard*; not Terminal.app, not VTE terminals), the box
can put copied text straight onto your clipboard through the terminal, with nothing installed
on your machine. Tell the stand-ins to do that for connections from this machine:

```ssh-config
Host mybox
    SetEnv LC_CLIPBOARD_SINK=osc52
```

The box's sshd must accept it (`AcceptEnv LC_*`, Ubuntu's default). In this mode only text
copies go out (a terminal cannot take an image), and reads are refused, so image paste still
needs the bridge. The stand-ins decide per request from the ssh connection attached right now,
so the same `box` session follows you between machines.

## Platform status

| Machine you sit at | Status |
|---|---|
| Linux, Wayland (`wl-clipboard`) | verified end to end (Fedora to Ubuntu 24.04 on aarch64) |
| Linux, X11 (`xclip`) | implemented, not exercised |
| macOS | bridge backend (`pbpaste`/`pbcopy`, `pngpaste` or AppleScript for images) and launchd agent written, **not yet run on a Mac**: run `./install.sh mybox --selftest` and report what fails |
| macOS, copy only via OSC 52 | verified (Ghostty) |
| Windows | not supported |

## When it does not work

- On the box: `tail -20 ~/.cache/clipboard-bridge.log` (every request the stand-ins made).
- A stand-in prints `no tunnel to 127.0.0.1:18377`: the tunnel is down; see
  [../tunnels](../tunnels/README.md#when-it-does-not-work).
- Linux bridge: `systemctl --user status clipboard-bridge.socket`. macOS:
  `launchctl print gui/$(id -u)/io.github.devbox-kit.clipboard-bridge`,
  `~/Library/Logs/devbox-kit-clipboard-bridge.log`.
- With the machine asleep or the tunnel down, the stand-ins fail in about 25 ms with one line
  on stderr, so Claude Code falls back instead of hanging.

## Tests

```bash
python3 -m pytest clipboard/tests -q
```

They assert the exact request the stand-in sends for a given command line (verb, MIME type,
selection, file vs stdin), because each of those has been wrong once: `xclip -t image/png -i
shot.png` once read stdin and wiped the clipboard while reporting success.
